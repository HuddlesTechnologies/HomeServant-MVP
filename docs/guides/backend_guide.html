1. What the backend is and what it runs on

The HomeServant API is the single source of truth for users, listings, bookings, payments, the marketplace, chat, notifications and the admin console. The Flutter app (web and mobile) is only a client of it.

PieceChoice and why
FrameworkNestJS 11 (TypeScript, Express 5). Its modules, guards and dependency injection keep auth and permission rules in one place.
DatabasePostgreSQL on Supabase, accessed through Prisma 7 with the pg driver adapter (@prisma/adapter-pg). Prisma gives a typed schema, generated queries and versioned migrations. The CLI's connection settings are in prisma.config.ts, not the schema.
Real-timeSocket.IO, through Nest's WebSocket gateway, for chat, notifications and live admin updates.
File storageSupabase Storage (public bucket). The client uploads directly using one-time signed links.
PaymentsPaystack: charges, webhooks, transfers and refunds, in an escrow model.
EmailResend in production; the console in development.
HostingRender (Docker web service on Node 22, render.yaml). Migrations run automatically at start-up. Prisma 7 needs Node 20.19+ or 22.12+.

All routes are served under the /api prefix, for example https://homeservant-api-c8w7.onrender.com/api/health.

3. How a request is handled

Set up in src/main.ts and src/app.module.ts:

  1. Helmet (security headers) and compression. trust proxy is on, so client IPs are correct behind Render's proxy.
  2. CORS: only the origins listed in CORS_ORIGINS can call the API from a browser.
  3. Rate limiting (ThrottlerGuard, global): 100 requests per minute per IP by default, and stricter on sensitive routes (for example the bootstrap route allows only 5 per minute).
  4. Guards on each route decide who may call it (section 5).
  5. ValidationPipe: request bodies are checked against their DTO classes. Unknown fields are rejected (whitelist and forbidNonWhitelisted).
  6. The controller calls a service, which reads and writes the database through Prisma.
  7. HttpExceptionFilter turns every error into { statusCode, message, error }. The app shows message directly, so write messages for end users.

4. Authentication and sessions

Tokens

  • Access token: a JWT signed with JWT_ACCESS_SECRET, valid for 15 minutes (JWT_ACCESS_TTL). It's sent as Authorization: Bearer ....
  • Refresh token: a JWT signed with JWT_REFRESH_SECRET, valid for 30 days (JWT_REFRESH_TTL). Only a hash of it is stored in RefreshToken. Each one can be used once: POST /auth/refresh revokes it and issues a new pair.
  • Logging out, resetting or changing a password, deactivating or deleting all revoke refresh tokens.
  • Changing either secret signs everyone out immediately. The Admin Guide's emergency procedure relies on this.

Sign-up and login flows

  • Signup: POST /auth/signup creates an unverified user and emails a code; POST /auth/verify-signup verifies it and returns tokens. Signing up again with an email that was never verified takes over the unverified record and sends a fresh code.
  • Emails ignore case: every email the API receives is trimmed and lower-cased (@NormalizeEmail() on each DTO, and Google's email too), so Ada@Example.com and ada@example.com are one account. Migration 20260928140000_lowercase_emails converted existing rows, skipping any two accounts that differ only by case (the migration file shows how to find them). Migration 20260928150000_email_lowercase_check then added database rules (CHECK (email = lower(trim(email))) on User and PendingAdmin) so, together with the unique index, case-variant duplicates can't be stored even by editing the database directly. Write emails lower-cased if you ever insert rows by hand.
  • Codes: 4 digits, valid 10 minutes. Any of the three most recent unexpired codes is accepted, so a resend doesn't invalidate the email the person already has; using one consumes them all. Five wrong guesses lock out until a new code is requested. Sending through Resend retries brief failures (rate limit, 5xx) and otherwise fails with "We couldn't send your code just now. Please try again in a minute." Sign-up codes, unread-message emails and admin alerts share one Resend account and its quota.
  • Sign-in pages: the client sends portal: TENANT or LANDLORD from those sign-in pages, ADMIN from the admin console (APP from older app builds = any non-admin). Right after the password check, assertPortalAllows refuses any other kind of account with a message naming the right page (e.g. "This is a landlord account. Please sign in on the landlord page."), so nobody is signed into a dashboard from the wrong page. Google sign-in sends the page too: an existing account of another role is refused before it's linked; a new account takes the page's role. Google always refuses admin accounts and never links Google to one, since it would skip their password, 2FA and the admin sign-in log.
  • Login: POST /auth/login can return:
    • tokens;
    • requiresTwoFactor (a code was emailed; finish with /auth/verify-2fa);
    • requiresReactivation (the account is deactivated; send the same request again with reactivate: true);
    • requiresEmailVerification (the email was never verified; a fresh signup code was sent).
  • Google: POST /auth/google verifies Google's ID token against GOOGLE_CLIENT_ID, then finds or creates the user. An existing email is linked to the Google account.
  • Profile completion: User.profileCompletedAt is set the first time a profile has every field signup requires, and is never cleared. The app's "finish your profile" redirect relies only on this flag, which is included in every auth response.
  • Password reset is by emailed code (/auth/forgot-password then /auth/reset-password). It's refused for admin accounts: another admin must reset those.

5. Roles, admin levels and permissions

User.role is one of TENANT, LANDLORD, VENDOR or ADMIN. Admins also have adminLevel: SUPPORT < MODERATOR < SUPER_ADMIN.

Guard / decoratorWhat it does
JwtAuthGuardRequires a valid access token and sets request.user.
RolesGuard + @Roles(...)Requires one of the listed roles. For admin routes it re-reads role and level from the database on every request, so demoting or removing an admin takes effect on their very next request.
AdminLevelGuard + @MinAdminLevel(...)Requires at least that admin level.
MustChangePasswordGuardBlocks an admin still on a temporary password (except routes marked @AllowMustChangePassword).

Some rules are more specific than a minimum level, so services check them themselves:

  • Admin password resets: you can't reset the password of an admin ranked above you.
  • Last super admin: the last super admin can't be demoted or removed.
  • Support chat access (chat/support-access.ts and ChatService.canWrite / assertCanRead):
    • non-participant admins can reach a support thread only while it's unclaimed;
    • a SUPER_ADMIN can read, but not write to, threads another admin is handling;
    • only a super admin can reassign.

The full admin permission table is in the Admin Guide.

7. Business flows

Bookings

  • Shortlet: the tenant requests dates (PENDING). The landlord accepts or declines (ACCEPTED / DECLINED). The tenant pays (PAID), and payment is released to the landlord.
  • Rental (house, apartment, self-con): creating the booking charges straight away (PENDING, then PAID_AWAITING_INSPECTION once paid).

    One live booking per tenant per property (BookingsService.create): a rental that's paid for or lived in (lease not ended) is refused; an unfinished checkout (PENDING) is reused and charged again rather than a second booking being created; a Shortlet with a request still PENDING/ACCEPTED is refused. assertRentalAvailable (common/rental-availability.ts) also refuses a rental that is occupied or already paid for by another tenant (RESERVING_STATUSES), both at create and at POST /bookings/:id/pay. findForTenant hides unpaid rental checkouts shadowed by a paid or newer booking for the same property (left over from older app versions), and returns landlordPaid (a RELEASED payment exists) and the tenancyAgreement.

    An inspection date is proposed and confirmed (INSPECTION_PROPOSED, INSPECTION_CONFIRMED). Moving in (MOVED_IN) releases the payment.

    Before move-in, the tenant can get a refund (REFUNDED) or the landlord can reject. A renewal charges again, near the end of the lease: GET /bookings/:id/renewal-quote returns what it would cost now (current price, unit and lease months, the price last paid and the new end date); POST /bookings/:id/renew takes {expectedAmount, expectedLeaseMonths} from that quote and refuses with 409 if the landlord changed either since, so a tenant is never charged an amount they didn't see (both fields are optional for older clients). A renewal doesn't touch Booking.priceSnapshot until it's paid; releaseRenewal then sets it to the rent actually paid and updates the TenancyAgreement's rentAmount, priceUnit and leaseEndDate, so the agreement always matches the current term.

    Monthly plan (Property.allowMonthlyPayment, non-Shortlet only): POST /bookings with paymentPlan: MONTHLY snapshots monthlyRent = ceil(yearly price / 12) and chargeBooking charges one month. That first month is held and released exactly like a full payment; move-in sets rentPaidThrough one month on. POST /bookings/:id/pay-month (open from 7 days before it's due, and when overdue) charges the next month; the webhook sees a MOVED_IN monthly booking with months left and calls releaseMonthlyInstallment (straight to the landlord, rentPaidThrough +1 month) instead of releaseRenewal. Renewing requires every month paid, charges the new term's first month, and keeps priceSnapshot as the yearly rent.

    Rent changes: PropertiesService.update compares the price, unit and rentDurationMonths before and after. If any changed, every tenant with a live booking on the listing (unpaid PENDING/ACCEPTED, paid and awaiting move-in, or a current MOVED_IN lease) gets one "Rent changed" notification with the old and new terms and what they mean for them. Payments, payouts and refunds always use the amount actually charged, so nothing already paid changes.

Payments (escrow)

All in PaymentsService. HomeServant charges the full amount through Paystack and holds it in its own balance (PAID_HELD). Later it transfers the recipient's share to their verified bank account (RELEASED) or refunds the payer (REFUNDED).

  • The platform keeps 5% on a release, or 0.2% on a rental refunded before move-in. Fees are in basis points, and amounts are converted to kobo only at the Paystack boundary.
  • Paystack confirms payments at POST /api/paystack/webhook. The signature (x-paystack-signature) is checked against the raw request body before anything is trusted. charge.success confirms a payment; transfer.failed / transfer.reversed put a payout back to owed. Set the Webhook URL in Paystack (Settings > API Keys & Webhooks) for each mode; see backend/README.md → Paystack setup.
  • Returning from checkout: Paystack sends the payer back to APP_URL with ?reference=. The web app calls POST /bookings/confirm-payment, which asks Paystack (verifyCharge) and, if it succeeded, runs the same handleChargeSuccess as the webhook (idempotent), so the booking shows as paid at once.
  • No double charges: before starting any rent charge, chargeBooking checks the booking's open (INITIATED) charges with Paystack; one that already succeeded is processed and the new charge is refused. Otherwise a new charge would mark the paid one FAILED and its late webhook would be ignored.
  • Payouts come from the Paystack balance (source: balance). releasePaymentToRecipient checks PaystackService.balanceKobo first; a payout the balance can't cover isn't sent or counted as an attempt, and payoutLastError starts with LOW_BALANCE_ERROR (Paystack's own "balance is not enough" refusal is rewritten the same way; see isLowBalanceError). retryLowBalancePayouts retries those every 30 minutes. PaystackService.mode reports test/live from the key prefix, because the two modes have separate balances.
  • Never twice: every payout and refund runs under withMoneyLock (one money action per payment at a time) and asks Paystack first (verifyTransfer / refundedSoFar). Rent payouts that fail no longer block the tenant; they wait on the admin Payouts & Refunds screen. Payouts to unverified landlords can be held (payUnverifiedLandlords).

Listings: ranking, featured ads, photos, hiding

  • Browse order (listing-ranking.ts, used by GET /properties without landlordId): available listings first (a booked-out shortlet or occupied rental after all of them); among available ones, promoted listings (admin adminBoost 1–2 not expired, or a running paid ad) fill one slot in every promotedSlotEvery (positions 0, N, 2N…), the rest newest first; equally promoted listings rotate by a daily hash. The page is cut from that full order.
  • Featured ads (PromotionsService, /properties/:id/promotions): quote, Paystack checkout (reference promo_…, metadata purpose: FEATURED_LISTING), and the webhook: PaystackController offers each charge.success to PromotionsService.handleChargeSuccess first, then to PaymentsService. Listings carry featured/featuredUntil.
  • Photo changes (PropertiesService.update): changing the cover or gallery uses one of maxListingImageChanges; the last locks photos for listingImageLockDays; after the lock a fresh allowance starts. The update is conditional on imageChangesUsed so a double submit can't spend one change twice. Responses carry imageChangesLeft, imageChangesAllowed, imageLockDays, imagesLockedUntil.
  • Taken rentals are hidden: general browsing (GET /properties without landlordId) leaves out non-Shortlet listings that are isOccupied or have a booking in RESERVING_STATUSES. A direct GET /properties/:id and the landlord's own list still return them.
  • Reviews (ReviewsService.upsert): only by a tenant with a booking on the property that has a RELEASED payment (the landlord has been paid), not merely paid into escrow.
  • Hiding: PATCH /properties/:id with isHidden (refused while occupied). Hidden listings are left out of GET /properties except for their own landlord (the route uses OptionalJwtAuthGuard to know who's asking) and POST /bookings refuses them.
  • Video: uploads to the property-videos folder only take mp4/mov/m4v/webm (and no other folder takes video); StorageService.assertIsOwnVideo checks the stored content type before videoUrl is saved.

Bans

AdminService.banUser (Moderator+) sets bannedAt/banReason, revokes every refresh token, emits account:banned to the user's live sockets, notifies and emails them. assertNotBanned (in auth.service.ts) refuses login, 2FA, Google sign-in and refresh with the reason (refresh checks it before "revoked", so an open app learns it was a ban). Banned landlords' listings are filtered from browse and can't be booked; a banned owner's shop is off the marketplace. unbanUser is Super Admin only (checked in the controller and the service).

Marketplace

  • An order is split into items, one payment each. The vendor ships (a delivery item gets a tracking record), the buyer confirms receipt, and the vendor's share is released.
  • If the buyer never confirms, a daily job releases the payment 7 days after shipping (or 7 days after payment for pickup items), unless there's an open report about that product.
  • Shops are opened by tenant accounts, must be approved by an admin, and a suspended shop's products are hidden.

Chat and support

  • Normal threads link two users, optionally about a property or an order, and are reused rather than duplicated.
  • Tenant/landlord messaging is tied to payment (ChatService.landlordTenantBlockReason), so both sides do business on the platform. A paid booking (PAID through MOVED_IN) opens messaging both ways. If there is no paid booking and a booking was refunded (the tenant's own refund, or the landlord rejecting a paid booking), messaging is closed both ways until the tenant pays again. With nothing paid yet, a landlord may reach out and the tenant may only answer a thread the landlord has already written in. Bookings count if they are on the thread's property, or on any of that landlord's properties for a thread not tied to a listing. The rule is checked when a thread is started and on every message; an existing thread still opens so its history stays readable, and GET /threads/:id/summary returns lockedReason, which the app shows in place of the composer. Support and marketplace order threads are not affected.
  • When messaging closes on a refund, PaymentsService posts a SYSTEM message (no sender) through ChatService.postBookingSystemMessage so both sides see why in the chat. A tenant's own refund adds it only to an existing conversation; a landlord's rejection starts one if needed, and the tenant's "Booking rejected" notification links to that chat.
  • A support thread starts with just the user. It sits in the shared queue until an admin claims it, either by opening it (PATCH /threads/:id/claim) or by replying, which is race-safe. It can then be transferred, reassigned by a super admin, or resolved.
  • ThreadTransferLog records every hand-off with a kind (CLAIM, TRANSFER, REASSIGN) and the actorId who made it. GET /threads/:id/handling-history (handling admin or super admin) returns the timeline, first handler and current admin. Reading a thread (PATCH /threads/:id/read) also marks the caller's notifications about it read, and for admins refreshes the Messages badge, which counts conversations with unread messages plus unclaimed support chats.
  • Support tools (SupportToolsController, admin only): GET|POST /threads/:id/notes (internal notes), PATCH /threads/:id/triage (topic, priority), GET /threads/:id/customer-context, GET|POST|PATCH|DELETE /support/saved-replies, and GET /support/admins (every active admin with level, on-duty, online and open-chat count, for transfers). Notes, triage and context need the same access as the thread: the handling admin, any admin while unclaimed, or a super admin.
  • Customers only ever see an admin's first name (adminPublicName: firstName, else the first word of fullName) in threads, summaries, messages, live message events and notifications; admins see full names. Admin invites take firstName/lastName.
  • The topic the customer picks (POST /threads/support) is stored on the thread, replaces an older topic on a still-open thread, and is shown to admins in the chat and in the "New support conversation" alert.
  • Calls: POST /threads/:id/calls {reason} (handling admin, anyone while unclaimed, super admins; on a non-support thread, an admin in it) records a SupportCallLog row and a SUPPORT_CUSTOMER_CALLED activity entry, and returns the customer's number; GET /threads/:id/calls lists them.
  • Auto-assignment (ChatService.pickAssignee): when a customer writes into an unclaimed support thread it goes to an on-duty, online admin with the fewest open support chats, ties broken by who was assigned longest ago; logged as AUTO_ASSIGN. Transfers and reassignments post a SYSTEM notice into the chat (postThreadSystemMessage).
  • Support dashboard: SupportChatStat keeps one row per support conversation, deliberately not linked to Thread so it outlives the 30-day cleanup. It is written as the chat moves along (first customer message, first admin reply, current admin, transfers, resolution, rating) and was backfilled for older chats. GET /support/metrics?days=7..90 (super admin, SupportMetricsService) returns live queue state, totals (median and 90th-percentile first reply, median resolution, rating), and breakdowns by topic, admin, hour, weekday and day. The customer can end their own support conversation with PATCH /threads/:id/end (resolved, closedByCustomer in the stats, SYSTEM notice, handler notified). No one can send into a resolved support thread. The customer rates with POST /threads/:id/rating (once, after resolution); the summary's canRate says when. When nobody is available, a one-time SYSTEM notice tells the customer they're queued.
  • Web Push (PushService, POST|DELETE /push/subscriptions, GET /push/public-key): every non-silent notification is also pushed to the user's subscribed browsers; subscriptions the push service reports gone (404/410) are deleted.
  • Notifications for unclaimed threads are collapsed into one per admin (NotificationsService.upsertThreadAlert) and cleared for everyone else on claim.
  • Admins marked Away get them silently (User.adminOnDuty).
  • Resolved support threads are removed after 30 days.

Notifications

NotificationsService.create is the only place notifications are created. It stores the row and pushes notification:new to the user's live connection, with a transient silent flag when the app shouldn't play a sound or show a banner.

8. Real-time: the WebSocket gateway

chat/chat.gateway.ts. Clients connect with auth: { token: <access token> }. Each socket joins:

  • user:<id> (its own room);
  • admins, if it's an admin;
  • thread:<id>, if it asks and is allowed.
Event (server to client)When
message:newA message is sent. It goes to the other participants, and to all admins while a support thread is unclaimed.
message:readThe other side read the thread.
notification:newA notification was created or updated (may be silent).
thread:claimedA support thread changed hands: claimed, transferred or reassigned.
thread:access-revokedThis socket was removed from a thread room it's no longer allowed in.
admin:badges-changedAn admin badge count changed. Sent by the services for reports, vendors and invites, and automatically (debounced) after any write to EvictionRequest, Payment or IdentityVerification.
listings:changedTo every connected app, debounced: browse results may have changed (any Property write, or a Booking status change). Tenants' apps quietly reload listings.

The last two are driven from one place: PrismaService is the client extended with a query hook ($extends, Prisma's replacement for $use middleware) that sees every write and calls onListingsChanged / onAdminQueuesChanged listeners (changesListings, changesAdminQueues). No code path that changes a listing or an admin queue can forget to tell clients. Because $extends returns a new client, PrismaService's constructor returns that client with the class's own methods attached (so instanceof PrismaService is false; nothing relies on it).

Online presence (PresenceService) tracks connected sockets per user and records lastActiveAt.

10. Files, email and other outside services

  • Uploads: POST /uploads/sign takes a file name and folder. Only image extensions and known folders are accepted. It returns a one-time Supabase upload link and the file's public URL, stored under <folder>/<userId>/<random>. Any endpoint that saves an image URL first calls StorageService.assertIsOwnImage, which checks it's in our bucket and really an image.
  • Email and codes: OTP_PROVIDER selects console (codes printed to the server log, for development) or resend (real email). MailService uses the same setting.
  • Email HTML: any name, title, reason or other typed text put into an email's HTML goes through escapeHtml (common/escape-html.ts), so markup a user types (for example in their name) can't render in someone else's email. The plain-text part is sent as-is.
  • Paystack: bank list, account-name lookup, charges, transfer recipients, transfers (and verifying a transfer by reference), refunds (and checking what was already refunded), webhook.
  • Private uploads: identity documents go to the private bucket via POST /verification/uploads/sign (photo or PDF); saved paths must be in the user's own folder and are checked to really be an image or PDF. Admins see them only through 10-minute signed links. They are deleted with the account.
  • Google: ID tokens are verified with Google's library against GOOGLE_CLIENT_ID.
  • Delivery: DELIVERY_PROVIDER selects console (default) or gig. The GIG integration is unverified scaffolding.
  • ID checks: ID_CHECK_PROVIDER selects console (default — checks nothing, so every submission waits for a moderator) or prembly (looks each ID number up with NIMC / the FRSC / INEC / Immigration through Prembly and compares the name on record with the name on the account). IdCheckProvider.check never throws — it runs inside signup, so a provider that is down returns ERROR and leaves the submission pending rather than failing the signup. A MATCH verifies a tenant outright; landlords always go to the queue. Lookups cost money, so one is only spent when the number is new or the last attempt gave no answer. Name comparison lives in src/id-check/name-match.ts. The live host is https://api.prembly.com/identitypass, authenticating on x-api-key alone; Prembly's older *.myidentitypass.com API hosts no longer answer at all, and the per-type endpoint paths are unconfirmed because every path under /identitypass/verification/ returns 401 before routing resolves — see the ID checks section of backend/README.md before changing them.

12. Running, migrating and deploying

Local

cd backend
cp .env.example .env         # fill in Supabase + two random JWT secrets
npm install
npm run prisma:migrate       # create/upgrade the local schema
npm run start:dev            # http://localhost:3000/api, reloads on change
npx tsc --noEmit -p tsconfig.json   # type-check

With OTP_PROVIDER=console, verification codes are printed in this terminal.

Changing the database

  1. Edit prisma/schema.prisma, with a comment explaining any new field.
  2. Run npx prisma migrate dev --name what_changed, or hand-write prisma/migrations/<timestamp>_<name>/migration.sql. Prefer additive changes (new nullable columns, or columns with defaults) so the live app keeps working during deploys.
  3. Commit the migration folder with the code.

Tests

The tests in backend/test run the real services against a real, disposable Postgres (only sockets, email and push are faked). They cover the tenant/landlord payment and refund rules, auto-assignment, claims, transfers and handling history, notes and saved-reply permissions, read state and the Messages badge, unread-message emails, push cleanup, the Admins invite badge, listing deletion, one booking per property (no double payments, confirm-payment, hidden duplicates, hiding taken rentals), rating only after payout, low-balance payouts and their automatic retry, and which writes trigger listings:changed / admin:badges-changed.

createdb hs_test
DIRECT_URL=postgresql://localhost/hs_test npx prisma migrate deploy
TEST_DATABASE_URL=postgresql://localhost/hs_test npm test

Every table is emptied before each test, so never point TEST_DATABASE_URL at a real database. GitHub Actions (.github/workflows/ci.yml) runs the type check, the migrations (and checks they match the schema), these tests, and the Flutter analyzer and tests on every pull request.

Resetting all chats

backend/scripts/clear_all_chats.sql is a one-off reset for testing. It deletes every conversation (with its messages, participants, transfer history and internal notes), chat notifications and support-dashboard rows, and leaves users, listings, bookings, payments, orders and saved replies alone. Run part 1 (a preview) and then part 2 (the delete, in one transaction) in the Supabase SQL Editor after taking a backup. Chat photos stay in Storage under chat/ unless deleted there too.

Deploying

Render builds the Docker image. On start the container runs npx prisma migrate deploy (applying any new migrations) and then node dist/main.js. The Prisma CLI is a production dependency and prisma.config.ts is copied into the image, so migrations use the pinned Prisma version. npm audit should stay at 0; package.json overrides pin patched deepmerge-ts and mysql2 inside the Prisma CLI. Deploy the backend before or together with any web release that depends on new fields.

14. Conventions for new code

  • Never trust the client. Every permission is checked in a guard or service, even if the app already hides the button.
  • Validate bodies with DTOs (class-validator). The global pipe rejects unknown fields.
  • Money goes through PaymentsService only; notifications go through NotificationsService only.
  • Race-safe state changes: use conditional updateMany ("only if still unclaimed") or transactions, not read-then-write.
  • Audit sensitive admin actions with ActivityLogService.log.
  • Allow for deleted people: optional relations can be null after an account is deleted.
  • Error messages are user-facing: the app shows them as-is.
  • Comment the why: the existing code explains reasons, not mechanics. Keep doing that.

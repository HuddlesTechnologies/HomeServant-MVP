1. What the app is and what it runs on

HomeServant is one Flutter app that serves four audiences:

  • Tenants, who find and rent properties;
  • Landlords, who list and manage properties and bookings;
  • Marketplace customers and vendors (a tenant can also open a shop);
  • Admins, through the admin console.

The same code builds the website (hosted on Vercel) and the Android/iOS apps. All data lives on the HomeServant API (see the Backend Developer Guide). The app holds no business data of its own beyond a few per-device preferences.

3. How the app starts

  1. main() calls assertSecureApiBaseUrl(), which refuses to run a release build pointed at a non-HTTPS API, then starts HomeServantApp.
  2. HomeServantApp creates the one AppState and the router, and calls AppState.load(). That restores device preferences and, if a login token is saved, fetches the user's profile (GET /users/me) and their starting data. Until it finishes, isLoaded is false and the router doesn't redirect anywhere.
  3. MaterialApp.router wraps every page in three layers, outermost first:
    • SessionExpiredGate: shows "you were signed out" when the refresh token dies.
    • AppLockGate: the optional PIN lock on phones.
    • NotificationBannerOverlay: the in-app notification banner, the admin alert sound and browser pop-ups.
Why one app instead of separate apps? Tenants, landlords, vendors and admins share most building blocks: sign-in, chat, notifications, uploads, payments. One codebase means one fix applies everywhere.

Why the marketplace has its own route and navigator: it has many screens of its own. Giving it one route means a single browser Back press from anywhere inside it returns to the dashboard, instead of skipping past the dashboard to an older page.

Redirect rules (appRedirect)

The router asks appRedirect(appState, location) on every navigation and whenever AppState changes. It's a plain function, so it's unit-tested in test/router_redirect_test.dart.

  1. Signed out on a protected page: sent to /get-started. Pre-auth pages (login, signup, code entry) are allowed.
  2. Signed in on an entry page (/, /get-started, /login, /signup): sent to /dashboard, or /admin for admins.

    The login and code screens themselves are deliberately not redirected. They become "signed in" partway through their own flow, and need to run their own next step, such as the App Lock PIN or finishing profile setup.

  3. Admins never land on /dashboard; they're sent to /admin.
  4. Unfinished profiles: a tenant or landlord whose server-side profileCompleted flag is false is sent from /dashboard or /marketplace back into the signup steps. Name and phone decide whether that's step 1 or step 2.

    This relies only on the flag the server sends with every login response. Checking individual profile fields instead used to send finished users back into setup on every login.

5. State: AppState

lib/state/app_state.dart is a single ChangeNotifier, provided at the top of the app. Screens read it with context.watch<AppState>() (rebuild on change) or context.read<AppState>() (one-off calls).

SectionHolds
Session and profileuserId, role, name, phone, address, photo, gender, occupation, marital status, profileCompleted, 2FA flag, bank details.
Authsignup, verifySignupOtp, login and loginWithGoogle (which return a LoginOutcome: success, two-factor needed, reactivation needed, or email verification needed), completeProfile, logout, deactivate and delete.
NotificationsThe list, unread count, mark read.
Properties, wishlist, bookingsThe public feed, a landlord's own listings, favorites, the tenant's and the landlord's bookings.
VendorWhether this user has a shop.
AdminadminLevel, adminOnDuty (server-side), and the device-only adminAlertSound and adminBrowserNotifications.
Device preferencesDashboard theme, notification toggles, banner auto-dismiss, App Lock.

Repositories are exposed on AppState (for example appState.chat, appState.admin, appState.uploads). Screens that manage their own lists, such as chats or admin tables, call them directly rather than storing everything in AppState.

Where it's saved: login tokens go to the phone's secure keychain, or to the browser tab's sessionStorage on web (section 10). Device preferences go to SharedPreferences, or sessionStorage on web. Profile data is never saved locally; it's re-fetched from the API at start-up.

Why one state object? The app's shared data is small and closely linked (the signed-in user drives almost everything). One well-organised object is easier for a small team than a store per feature. If it grows much further, splitting it by area is the natural next step.

6. Talking to the backend

Where the API is

lib/api/api_config.dart reads API_BASE_URL from the build command (--dart-define=API_BASE_URL=https://.../api). The Vercel build sets it to the Render server.

ApiClient: one HTTP client for everything

  • Adds Authorization: Bearer <access token> to every request, except auth calls marked skipAuth.
  • On a 401, calls POST /auth/refresh once, saves the new token pair, and retries the request. Several requests failing together share one refresh, because the server's refresh tokens can only be used once. If refreshing fails, onSessionExpired signs the app out and shows the "session expired" message.
  • call(...) turns every network error into an ApiException carrying the server's own message, so screens simply show e.message.

Repositories: one per backend area

RepositoryBackend area it calls
AuthRepository/auth/*: signup, verify, login, Google, 2FA, refresh, logout, password reset and change, deactivate, delete.
UsersRepository/users/me, /users/me/bank-details.
PropertiesRepository/properties.
BookingsRepository/bookings: create, pay, inspection, move-in, refund, renewal quote and renew, landlord responses, tenancy agreement. Renew Lease (History) fetches the quote, confirms the amount with showConfirmSheet (its notice flags a rent increase), then opens Paystack; the lease updates when the webhook confirms payment.
FavoritesRepository, ReviewsRepository/favorites, /reviews.
ChatRepository/threads: inbox, messages, support chat, claim, resolve, transfer, reassign, summary.
NotificationsRepository/notifications.
VendorsRepository, MarketplaceProductsRepository, MarketplaceOrdersRepository/vendors, /marketplace/products, /marketplace/orders.
PaystackRepository/paystack/banks and account-name lookup for bank details.

A typical request, end to end

Screen button tap
  -> context.read<AppState>().someAction()      (or a repository directly)
  -> XRepository.method()  ->  ApiClient.call(() => dio.post('/path', data: {...}))
  -> server responds with JSON
  -> Model.fromApi(json)  ->  AppState updates fields + notifyListeners()
  -> screens using context.watch rebuild

Uploading photos and files

  1. The user picks a file (upload_picker.dart).
  2. UploadsRepository.upload reads its bytes and works out its type from the content. On web the picked file is a blob: address, which is why the security policy allows blob:.
  3. It asks the API for a one-time upload link (POST /uploads/sign) and sends the bytes straight to Supabase Storage with PUT.
  4. It saves the returned public URL on the record, for example PATCH /users/me {profilePhotoUrl}. The server checks that the URL is really one of its own images before accepting it.

Payments

Booking a property or buying a product returns a Paystack authorizationUrl, which the app opens with url_launcher. The server learns that the payment succeeded from Paystack directly, via its webhook, and the app picks up the new status on its next refresh or live notification.

Google sign-in

On phones, our own button opens the native account picker. On web, Google's own rendered button is shown, because on web that's the only way to get the ID token the server verifies. Both end in AppState.loginWithGoogle.

7. Real-time updates, sounds and browser pop-ups

ChatSocketService opens one Socket.IO connection after login, authenticated with the access token, and turns server events into Dart streams.

EventWhat the app does
message:newOpen chat screens append the message; inbox lists reload.
message:readYour sent messages show "Seen".
notification:newBanner, list refresh, admin sound and browser pop-up, unless the push is marked silent.
thread:claimedAdmin queues reload, the matching banner is dismissed, and open chats re-check whether you can still reply.
thread:access-revokedAn open chat switches to read-only with a notice.
admin:badges-changedThe admin console reloads its badge counts.

Admin-only extras, all in NotificationBannerOverlay:

  • Alert sound (ChatSoundService): at most one sound per 10 seconds, only if the device's sound setting is on.
  • Web Push (everyone, web only): offerBrowserNotifications offers to turn notifications on once per page load on each dashboard. AppState.enableWebPush asks the browser from that tap, registers web/push-sw.js (scope ./push/, so it never touches Flutter's own files) and sends the subscription to the backend; syncWebPush re-registers after every sign-in, and sign-out unsubscribes this browser. The worker skips showing a push while the app is open and in view, and uses the same tag as the in-tab pop-up so they never double up.
  • Browser pop-ups (services/browser_notifications*.dart): shown only when the console tab isn't in view. They use the browser's own Notification feature, through a web-only file loaded with a conditional import. It does nothing on phones.

9. Look and feel

  • Fonts: Quity for headings, Givonic for body text. Both are bundled with the app, never downloaded (AppTextStyles). Neither has ₦, dashes, bullets, ellipsis or arrows, so a bundled subset of DejaVu Sans (HSFallback, assets/fonts/) is set as fontFamilyFallback on every style and on the theme. Without it the browser fetches a fallback font from Google at runtime and those characters render blank if that fails. When you add a new symbol to the UI, check it's covered, or re-run pyftsubset with the extra range.
  • Fixed brand colors: AppColors (navy, gold, sand and so on). The auth screens and admin console use these directly.
  • Role colors: UserRole gives the auth screens navy for tenants and gold/sand for landlords.
  • Dashboard themes: DashboardTheme offers user-selectable palettes (Classic, Midnight, Sand) for the dashboards, marketplace and vendor screens. Each theme defines matching pairs: background/foreground, surface/onSurface, accent/onAccent.
The contrast rule (from CLAUDE.md): every piece of text needs an explicit color that is checked against the exact background it sits on. Only use each theme pair together; background/foreground flip between themes. When giving a field a custom fill color, always pass its text color too. Invisible text has been this app's most common bug.

Layouts are designed for phones first and centred with a maximum width on larger screens (ResponsiveCenter).

10. Web-specific setup

Vercel build

vercel.json clones Flutter, runs flutter build web --release --dart-define=API_BASE_URL=..., and serves build/web. Every pull request gets a preview deployment.

Content-Security-Policy

The site sends a strict security policy. Anything the app loads from elsewhere must be listed in vercel.json; if something silently stops working on web, check here first.

AllowedWhy
https://www.gstatic.comFlutter's rendering engine (CanvasKit).
https://fonts.gstatic.comFlutter's fallback fonts. Without it, text in default fonts rendered invisible.
blob: (connect)Reading a picked photo before upload. Without it, uploads failed with "could not reach the server".
https://*.supabase.coUploading to and showing images from storage.
API host (https and wss)The REST API and the live connection.
https://accounts.google.comGoogle sign-in button and popup.

Sessions per tab

On web, login tokens and preferences are kept in sessionStorage, which is separate for each tab. That way two people signed in on different tabs of the same browser never share a session. The trade-off is that opening a new tab means signing in again.

Web addresses

The app uses hash-style addresses (/#/admin-login), so any page can be refreshed without extra server setup.

11. Testing, building and conventions

flutter pub get
flutter analyze            # must report "No issues found!"
flutter test               # all tests must pass
flutter run -d chrome --dart-define=API_BASE_URL=http://localhost:3000/api
flutter build web --release --dart-define=API_BASE_URL=https://<api-host>/api

Conventions

  • New backend call: add a method to the relevant repository, wrap it in _client.call, and parse the response with a model's fromApi.
  • New named page: add a GoRoute and decide whether it's a pre-auth page (_preAuthPaths). Add a test to router_redirect_test.dart if it affects redirects.
  • Before copying a screen: reuse the shared widgets in lib/widgets. Parameterise by role instead of duplicating; earlier copies drifted apart and caused bugs.
  • Web-only code: put it behind a conditional import with a no-op stub, as in browser_notifications*.dart and google_web_button*.dart.
  • Permissions: never rely on hiding a button. The server must refuse the action too.
